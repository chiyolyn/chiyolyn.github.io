在 AI 原生产品上做得好的产品经理，有怎样的特质？

时任 Anthropic Claude Code 与 Cowork 产品负责人 Cat Wu 的回答是，想清楚「怎么缩短从想法到用户手里的时间」，并定义清楚「我的产品里哪些任务必须开箱即用」。

下文整理和转译自 Lenny's Podcast。这期对话里的许多行动，马上就能参考。但渐渐我又意识到，达成某些结果好像不源于单个极度卓越的个体，而来自一个优秀的、以某种方式联结的组织。

1. 让想法更快变成产品抵达用户

Cat 多次提到「更快」，并认为流程和团队预期比用什么模型更影响发布速度：我们想消除发布路上的一切障碍，想让团队里的每个人都觉得有能力把一个想法从「只是个想法」推到「上线」，一周以内搞定，有时候甚至一天。

如何「更快」？设定清晰的目标；建立可复用的发布流程；搭建跨团队的协作框架，降低发布流程的摩擦。

Cat 说，永远有无数风险和棘手局面——你要是对每件事都过度焦虑，很快就会 burnout。

这会很难，但我很兴奋要去搞定它；我会尽全力，我知道自己不会完美，但我能安心睡觉，因为我尽力了。
「研究预览」（research preview）这类形式能降低产品发布早期新功能的心理负担。
以前发一个带 bug 的功能会让我睡不着觉；现在我能与它共处了，因为我知道：我们会很快拿到反馈，下个版本就修掉。

所以一定要做到的是：让想法快速上线抵达用户，并让它回来时带着答案。

Cat Wu 团队有严格的指标体系，每周和团队复盘；有一份「团队原则」清单。

我们把这些都写明白，是为了让团队里每个人都觉得自己理解这个业务是怎么运转的，知道什么对我们是重要的、我们愿意做什么样的取舍。这样每个人就能自己做决策，而不会觉得自己被 PM 或其他干系人卡住。

放到更大的维度，则是「把使命（把安全的 AGI 带给全人类）放在任何单一产品线之上」，所以能更快地在全公司范围内做决策，然后统一执行。

2. 产品经理这个角色：Just do things

Cat Wu 的团队构成：PM 几乎都当过工程师，或真的在 Claude Code 提交代码；设计师以前都是前端工程师。Cat 自己也是工程师出身，加入 Anthropic 之前短暂做过 VC。

工程背景之所以特别有用，是因为你对「一件事应该有多难」有更好的直觉，而这常常是决定做什么的因素。如果一件事很简单，与其开会争论，不如花一小时直接做掉；但如果一件事很难，你事先就知道团队要付出多大代价才能把它发出去。这对排优先级很有帮助。
工作正变得越来越无固定形态，一个优秀的 PM 要能看清所有的缺口、判断哪些优先级最高，然后想明白：「我是该去学这项技能，还是用我现有的技能来解决这个挑战。」现在的环境奖励的是那种能戴很多顶帽子、随时换帽子、而且对「自己该干什么活」没有自我包袱的人。
我甚至觉得「岗位」这个东西是虚的。如果你理解约束条件，就能想明白自己能做什么，然后就尽快去做；做错了就从中学习、道歉或者修好它。Just do things.

「这种构成能帮团队在工程师中建立信任，也让团队跑得更快。」不知道国内大厂的朋友们怎么看。人在其位，似乎更容易觉得自己对这个领域更专业；或出于某种职场规则，人不得不遵守自身角色的发言与行动边界。有工程师背景的 PM 会更容易在 dev 团队中建立信任，还是仍然无法打破团队之间的围栏？是先有这样的「环境和奖励」，还是先有这样「没包袱的人」？

3. 一个月后的产品长什么样

Cat 说，最难的技能是：能定义「一个月后产品应该长什么样」。

为「超级 AGI 模型」做产品其实很容易；难的是为「当下的模型」做产品。

她的建议是：其一，花大量时间用模型，对「模型为什么做了那个决定」保持好奇，就能看清是什么误导了它，接着修 harness、把这个缺口补上；其二，找到那些你最信任、能对模型给出准确反馈的用户；其三，写 evals。

做一些「现在还不见得能跑通」的产品其实非常重要——这样你才知道差在哪。等新模型来了，直接把它换进你早就做好的原型里，看看新模型能不能把这个差距补上。

谈到有哪些东西是为了更大的好处（例如「更快」）而主动牺牲的，Cat Wu 的回答是「产品一致性」。

现在 AI 跑得太快，要验证的想法太多，我们有时确实会做出互相重叠的功能——很多时候是因为内部有两种我们都喜欢的形态，想让外部用户来告诉我们哪个更好。但对新用户来说，这意味着他可能搞不清「要做成 X 这件事，最佳路径是哪条」。

所以 Cat 认为还需要继续做的，是让用户少点「被放在一条越跑越快的跑步机上」的感觉。「希望用户能觉得：打开工具就行，工具自己会教我需要知道的东西，让我感觉自己是被带着往前走的。」这也呼应了开头提到的，定义清楚「产品里哪些任务必须开箱即用」。

几乎每一份关于产品的访谈，都会提到产品品味（product taste）。Cat 理解为「决定写什么」：判断哪些值得做、正确的做法是什么，需要非常多的用心和品味。

4. 关于办公场景的一些产品

Cat Wu 和 Lenny 都认为 Slack 是重要的通信基础设施。

Anthropic 整个公司跑在 Slack 上——它差不多是我们公司的操作系统。

如果你刚开始用 Cowork，第一件要做的事是把跟你角色相关的数据源全部接上——Cowork 只有拿到它需要的全部上下文，才能帮你组织出好的结果。

Cat Wu 也提到，Claude Code 让做任何定制应用的门槛变低，所以可以在公司里看到一波「个性化工作软件」的爆发——大家为特定场景自己造工具，而不是去凑合用那些不完全合身的现成软件。

5. 用不上的原型和 95% 的自动化，都没太多价值

大部分人的工作中有两部分：热爱的创造性部分，深恶痛绝的繁琐部分。尽量让 AI 完成后者。

找出那些可以交给 Claude 的重复性工作，把自动化打磨到成功率非常高，然后把精力放到「我还能为团队、为产品、为公司多做什么」上。

Cat Wu 说，一个 95% 的自动化没多大价值，因为最后那 5% 到 10% 更花时间。

我见过一些用户做自动化，做到 90%、95% 的准确率就放弃了。但如果一个自动化不是 100% 可靠，它就算不上真正的自动化。要打磨到「它真的 100% 都能跑对」。

与其用 AI 搭原型应用、折腾工作流，不如试试做那种「你自己真的每天都在用」的应用。如果你做的原型应用并不能帮你多干活，那 AI 就没有真的给你的每一天增加价值。

Just do things.

[0:32] 开场：Claude Code 背后的产品负责人

Lenny：今天的嘉宾是 Cat Wu，Anthropic 旗下 Claude Code 和 Cowork 的产品负责人。Cat 正站在 AI、产品与构建方式这场变革的中心，她和她的团队正在打造那个最能改变我们所有人做产品方式的产品。她的洞察和心法非常多，这期节目绝对不能错过。Cat，欢迎来到节目。

Cat Wu：谢谢邀请。

Lenny：我有一肚子问题。你能来我真的太兴奋了。我想先让大家理解一下你和 Boris[1] 是怎么分工的。Boris 大家都认识——他上我那期是本播客有史以来播放量第一的一期（没别的意思，不给你压力）。他创造了 Claude Code，带着团队，一天能从手机上提交无数个 PR。说真的，我觉得 Claude Code 的成功、Cowork 以及你们做的一切，外界给你的认可还不够。帮我们理解一下：你在团队里的角色是什么？你和 Boris 怎么配合、怎么分工？Claude Code 团队上的 PM 到底长什么样？

[1] Boris：Boris Cherny，Claude Code 的创建者兼技术负责人（tech lead）。

Cat Wu：能和 Boris 共事我觉得自己很幸运。他是特别好的思想伙伴。他是我们的技术负责人，更是产品的愿景家——他非常擅长定方向：三个月、六个月后产品应该是什么样，那个「完全 AGI 信念版[2]」（the AGI-pilled version）的产品是什么样。
而我很大一部分职责是想清楚：从今天到那个三到六个月后的愿景，路径是什么。我花在跨职能协同上的时间更多：确保市场、销售、财务、算力容量等等团队都认同计划、往同一个方向划桨，确保功能一旦 ready，发布路上没有任何障碍。
我觉得我们合作得好，很大程度上是因为我们像「心灵融合」（mind-meld[3]）一样默契——但分工的界限其实出奇地模糊。大概 80% 的事我们想得一模一样，然后有 20% 是我更在乎、我来推进，还有 20% 是他更在乎、他来推。

[2] AGI-pilled：硅谷圈流行语，源自「red-pilled」（《黑客帝国》梗），指一个人对 AGI 会很快到来的信念程度。「剂量刚刚好」指既不盲目乐观也不保守。

[3] mind-meld：源自《星际迷航》中瓦肯人的「心灵融合」，此处形容两个人想法高度同步、像共用一个大脑。

[3:20] 「更快」是怎么做到的：流程、预期与 PRD

Lenny：好，正式开始前你跟我分享过一件事：你在不停地面试几百个 PM。要是每次有人找我内推 Anthropic 的 PM 岗位我都能拿五美分，我现在都有 300 亿 ARR 了。Anthropic 就是大家最想去的地方，没有之一。所以我完全能想象你面试了多少 PM。你还跟我说，你看到很多人的做法——不对，是他们理解「怎样才能成为成功的 AI 产品经理」的方式就错了。聊聊你看到了什么，以及今天想成功到底需要什么。

Cat Wu：我觉得在 AI 之前，技术变革的节奏慢得多，所以你可以按 6 到 12 个月的周期做规划。因为发功能的速度慢，所以工作的重心更多是跟各个合作团队协调——确保他们发布的功能能为你的功能解除阻塞、打通依赖，因为那时候代码很昂贵。
而现在，有了 AI，工程被极大加速，模型能力提升飞快，我们很多产品功能的交付周期从 6 个月降到 1 个月，有时候 1 周甚至 1 天。这就意味着我们必须确保产品发得飞快。对 PM 来说，这意味着：少花点心思去跟合作团队对齐那种跨好几个季度的路线图，多花心思去想——怎么才能最快把东西发出去？怎么才能搭出一块「概念试验角」，让工程师或 PM 有了想法，一周内就能送到用户手里？我认为在 AI 原生产品上做得最好的 PM，是那些能想清楚「怎么缩短从想法到用户手里的时间」、并且能定义清楚「我的产品里哪些任务必须开箱即用」的人。

Lenny：我喜欢你这个说法的地方在于：大家还没真正理解自己需要跑多快，以及现在这个工作有多大一部分就是「帮团队跑快」。那具体怎么做？你平时做什么？除了能用上最先进的模型之外，你们的 PM 团队做了什么来帮助团队这么快？

Cat Wu：我觉得第一件事是设定清晰的目标。因为 LLM 太通用了，这会带来很大的模糊性：我们在为谁构建？要解决什么问题？最高优先级的使用场景是什么？一个好的 PM 要能明确说出来：「我们的核心用户是专业开发者。这个功能要解决的主要问题是权限弹窗太多、用户已经弹窗疲劳了。场景是：我们要让企业里的专业开发者能安全地做到零权限弹窗。」这就定出了一个非常清晰的目标，因为它排除了大量「减少权限弹窗」的其他可能方案，让团队知道该往哪打。
第二件重要的事是建立一个可复用的发布流程。在 Claude Code，我们几乎所有功能都以「研究预览」（research preview[4]）的形式发布。发布时我们会清楚地标注，让用户知道这是早期产品、只是一个想法，是我们想收集反馈、持续迭代的东西，未来不保证一直维护。这降低了我们发布一个东西的心理负担——一两周内就能把东西发出去。
第三件事，PM 要帮团队搭好协作框架，让大家知道什么时候该拉跨职能伙伴进来、以及对这些伙伴的预期是什么。比如我们工程、市场和文档团队之间有一套非常紧的流程：工程师觉得某个功能 ready 了、内部也自己用过（dogfooding[5]）了，就把它发到我们的「常青发布频道」（evergreen launch room）里，然后负责文档的 Sarah、负责产品营销的 Alex，还有 DevRel[6] 的 Tar 和 Lydia 就会接棒，第二天就能把市场发布物料做出来。正因为有这套紧凑的流程，任何工程师发布东西的摩擦都很低——而搭建这套流程正是 PM 这个角色该干的事。

[4] research preview：比正式版更早、更实验性的发布通道，功能可能不稳定，用于收集真实用户反馈。

[5] dogfooding：「吃自己的狗粮」，指公司员工日常使用自家产品来发现问题。

[6] DevRel：Developer Relations，开发者关系，负责面向开发者社区的布道、文档和反馈收集。

Lenny：PRD[7] 在这里面是什么位置？你说目标非常重要——要对齐「成功长什么样」「这是为谁做的」「不是为谁做的」。那你们还写 PRD 吗？还是就列几个要点？在 AI 时代这件事是怎么演变的？

[7] PRD：Product Requirements Document，产品需求文档。

Cat Wu：我们做两件事。第一，我们有非常严格的指标体系，每周和整个团队一起做指标复盘。目的是确保每个人都深度理解我们业务的方方面面：核心目标是什么、趋势怎么走、是什么在驱动它们。第二，我们有一份「团队原则」清单，里面包括我们的核心用户是谁、为什么是他们。我们把这些都写明白，是为了让团队里每个人都觉得自己理解这个业务是怎么运转的，知道什么对我们是重要的、我们愿意做什么样的取舍。这样每个人就能自己做决策，而不会觉得自己被 PM 或其他干系人卡住。

Lenny：我很喜欢你说的这些——说到底还是「未来依然需要 PM」。现在到处都在说「还要 PM 干嘛？直接让工程师发布和构建就行了」。

Cat Wu：哦，我们其实还是写 PRD 的。对于那些方向特别模糊的功能，写一页纸确实有帮助：目标是什么、让人愉悦的使用场景是什么、目前有哪些需要修复的失败模式。另外偶尔也有一些项目——尤其是重基础设施的——确实要花好几个月，这些情况下我们还是会写 PRD。

Lenny：我想再深挖一下你们怎么能跑得这么快。我从没见过 Anthropic 这种发布节奏——有人做了一张 Anthropic 的发布日历， literally 每天都有重要功能或产品上线。网上很多人问的一个问题是：你们最近搞出了一个叫 Mythos 的模型，还在预览阶段，因为它太强了，大家有点怕它能做的事。你们自己是不是已经在用了？这是不是你们能跑这么快的部分原因？

Cat Wu：我们已经连续好几个季度跑得很快了，所以这不能完全归功于 Mythos。Mythos 是一个极其强大的模型，我们内部确实在用自家模型，我觉得这对发布速度有一点提升，但它解释不了提升的大头。我认为大头在于流程和团队预期。我们的流程极轻：我们想消除发布路上的一切障碍，想让团队里的每个人都觉得有能力把一个想法从「只是个想法」推到「上线」，一周以内搞定，有时候甚至一天。

Lenny：太强了。一边有最好的模型，一边还在做产品，这是什么神仙优势。

Cat Wu：能和最前沿的模型共事，我们确实很幸运。

[11:41] 支线：源码泄露与 OpenClaw

Lenny：天呐，这优势太夸张了——做出一个东西，然后自己用它，然后加速得更快。太有意思了。我还想问几件「支线任务」式的事。Anthropic 最近动作太多了，我特别想听听你的看法。第一件：大概一周前，Claude Code 的整个源代码泄露了，被人传到了外面，似乎是有人犯了错。你能评论一下吗？发生了什么？哪里出了问题？大家该知道什么？

Cat Wu：我们看到之后立刻做了调查。结论是人为失误：一位同事用 Claude 辅助写 PR，那是一个关于我们发布包流程的更新，而且它其实经过了两层人工审核。所以这纯粹是人为失误，我们已经在流程上做了加固，确保这类事不再发生。

Lenny：这个人还在 Anthropic 吗？他现在还好吗？

Lenny：哇，这正是那个大问题——角色确实在融合——工程、产品、设计这几个圆圈，正像维恩图一样重叠到一起。很多人想问的是：如果你是工程、产品或设计出身，哪项核心技能会最值钱？在 Anthropic、在 Claude Code，我能看出工程能力很值钱。我好奇的是在其他公司，设计背景转 PM 是不是更吃香？

Cat Wu：我还是觉得归根结底是产品品味（product taste）。写代码的成本越来越低，更值钱的就是「决定写什么」：这个功能的正确 UX 是什么？用户体验它最愉悦的方式是什么？我们的 GitHub 上躺着几万个 issue，天南海北什么需求都有，要判断哪些值得做、正确的做法是什么，需要非常多的用心和品味。这种能力可以来自任何背景，但它是目前最重要的东西。
工程背景之所以特别有用——至少在接下来几个月——是因为你对「一件事应该有多难」有更好的直觉，而这常常是决定做什么的因素。如果一件事很简单，与其开会争论，不如花一小时直接做掉；但如果一件事很难，你事先就知道团队要付出多大代价才能把它发出去。这对排优先级很有帮助。

Cat Wu：我觉得「值钱的技能组合」本身变化得就很频繁，超过几个月的事情很难预测。所以我不是在预言具体会发生什么转变，而是在说：大的转变一定会发生。

Cat Wu：对，我只是说每隔几个月编程能力就会有一次大跃升，随之改变的是其他角色的价值。

所以现在的环境奖励的是那种能戴很多顶帽子、随时换帽子、而且对「自己该干什么活」没有自我包袱的人——只要能让团队跑得更快。

[12] 第一性原理思维（first principles thinking）：不从惯例和类比出发，而是回到最基本的约束和事实重新推导解决方案的思考方式。

Lenny：我喜欢这个回答。我一直在问站在你这个位置上的人——那些处在 AI 能力最前沿、用最新工具构建产品的人——一个问题：在到达超级智能之前，人类大脑还会在哪些地方长期有用、不可或缺？从你刚才说的，我听到的是：选择做什么、判断市场走向、决定优先级；然后是判断做出来的东西好不好、对不对，并以某种早期形态把它推出去。我理解得对吗？至少在未来几个月内，人类大脑还有哪些地方会持续有用？

Cat Wu：我觉得人类仍然提供了一种模型不具备的常识。任何一次产品发布都有一千个活动部件，有些很小，但出错的点永远很多。模型并不总是能很好地感知：所有的利益相关方是谁、他们之间什么关系、各自的偏好是什么、用什么合适的场合和方式跟他们沟通、让他们持续支持。这类更偏隐性常识、偏情商的知识，现在仍然非常值钱。当然我们希望模型在这方面变强，我觉得它们会的，但眼下差距还在。

Lenny：作为一个身处其中的人，你怎么应对这种持续不断的剧变？你就在龙卷风的风眼里——也许风眼反而是平静的——你是怎么跟上所有事情的？在这一路狂奔的疯狂里，你是怎么保持心态不失衡的？

Cat Wu：我觉得我们团队全是主动拥抱混乱的人。我们尽量笑着面对每一个挑战，因为永远有无数事情在同时发生，永远有无数风险和棘手局面——你要是对每件事都过度焦虑，很快就会 burnout。所以我们招人时特别看重一种特质：看到挑战时想的是「这会很难，但我很兴奋要去搞定它；我会尽全力，我知道自己不会完美，但我能安心睡觉，因为我尽力了」。

Lenny：这算是对「未来什么技能重要」的一个有趣回答。我忘了是谁说的——可能是 Ben Mann[13]——「今天是这个世界往后最正常的一天」。

[13] Ben Mann：Anthropic 联合创始人之一。

Cat Wu：对，确实只会越来越难。经常有这样的周：周日晚上冒出一个 P0[14]，周一早上又来一个，周一下午直接升级成 P0000，你回头一看：「天，我周日居然为那个 P0 那么焦虑。」但你必须承认：你能做的就这么多，你得睡好觉，第二天才能做出好决策，然后极度无情地排优先级——什么事是必须要做对的？剩下的就学会放手。我们发布的产品里，有些没有我希望的那么精致。但我们的头号目标是赋能专业开发者，只要一个功能不阻塞核心场景，没做好也没关系——我们会收到反馈，下个版本修。以前发一个带 bug 的功能会让我睡不着觉；现在我能与它共处了，因为我知道：我们会很快拿到反馈，下个版本就修掉。

[14] P0：优先级最高的事故/任务分级（Priority 0，线上严重故障级别）；「P0000」是夸张说法，形容紧急程度层层升级。

Cat Wu：对，没有这种心态的话很容易 burnout。我们招人也比较偏向在行业里待过一段时间、经历过大起大落的人——他们清楚什么能给自己充电，也知道怎么长期维持能量。这一点帮了我们很多。

[23:23] 高频发布的代价：牺牲产品一致性

Lenny：太有意思了。我接着问角色模糊化这件事：工程师在变成 PM，所有人都是所有人。在这个世界里，我们失去了什么？会不会失去职业阶梯和清晰的晋升路径？会不会牺牲设计一致性、代码质量？肯定是有代价的。你觉得有哪些东西是你们「为了更大的好处而主动牺牲」的？

Cat Wu：我们牺牲的是产品一致性。以前写代码很贵，你会精心规划整个产品线：每个产品之间什么关系、各自的场景是什么、怎么集成，基本上一个场景对应一个产品。现在 AI 跑得太快，要验证的想法太多，我们有时确实会做出互相重叠的功能——很多时候是因为内部有两种我们都喜欢的形态，想让外部用户来告诉我们哪个更好。但对新用户来说，这意味着他可能搞不清「要做成 X 这件事，最佳路径是哪条」。我们需要做更多用户教育，帮大家理解核心功能是什么、最佳实践是什么。我觉得这就是高频发布的代价。用户也觉得跟不上最新动态：传统产品一个月或一个季度发一个功能，用户很容易跟上——一个月看一次就行，半年不看也不觉得错过什么。而这些 agent 工具——不只是 Claude Code 和 Cowork，整个生态都是——让人觉得必须每天刷 Twitter 才能知道最新发生了什么。我觉得我们还能做更多事，让大家少点「被放在一条越跑越快的跑步机上」的感觉。我特别希望用户能觉得：打开工具就行，工具自己会教我需要知道的东西，让我感觉自己是被带着往前走的。

Lenny：对，我看到你们前几天发了个很有意思的功能，好像是 /powerup——带你过一遍 Claude Code 所有很酷的用法和最佳实践。就是出于这种考虑吗？

Cat Wu：完全正确。我们以前其实不想做 PowerUp 这类东西——我们的原则是产品应该足够直观，不需要教程。但后来我们意识到，功能实在太多了，用户对一个内置的新手引导需求太强，于是我们稍微偏离了「绝不做 onboarding 流程」的原始原则，加了这个功能。因为太多用户想知道：「100 个功能里，哪 10 个是我必须用的？」所以我们做了这个东西。

[28:32] Anthropic 为什么能后发先至：使命与聚焦

Lenny：这真是个魔幻的世界。而且 Anthropic 在 B2B 企业市场做得非常成功——按传统，2B 不该这么高频发东西，可能一个季度发布一次，跟「每天都有新东西」完全相反。顺着这条线说：Anthropic 这波增长简直不像这个星球的。它起步时远远落后——融资最少的那批公司之一，没有分发渠道，也不是先发者，OpenAI 遥遥领先，当时看起来 Anthropic 根本没机会在长期竞争中立足。现在它却在碾压那些大公司，ARR 大概 110 亿美元、月增长率高得吓人——等这期节目播出时数字估计又涨了。身在内部，你觉得是哪几个关键成分让 Anthropic 能这么成功、后发先至？

[31:58] Claude Code、桌面版、Cowork：什么时候用哪个

Lenny：好，我们聊了 Claude、Cowork 这些产品。我想让大家真正搞明白，也好奇你自己是怎么用的：有 Claude Code，有 Claude 桌面版和网页版，有 Cowork——什么时候用哪个，最好的理解方式是什么？

Cat Wu：我在终端里用 Claude Code，主要是发起一次性的编码任务、并且想用所有最新功能的时候。CLI 是我们最初的产品形态，新功能往往也最先落在上面，所以它是所有工具里最强的。一次想跑一个或少数几个任务时，我就用它。桌面版在需要前端工作的场景里特别好用：我特别喜欢预览功能——做网页应用时我会在桌面版里开着右侧预览窗格，一边跟 Claude 聊天一边实时看到网页的变化。它也更适合喜欢图形界面的人：终端对非技术背景的人来说很陌生——弹出一堆吓人的授权弹窗，也没法像其他产品那样点点点。很多人就是不喜欢终端，如果你是这种人，我强烈推荐试试桌面版。桌面版还适合做全局总览：你可以在里面看到 CLI 终端会话、其他桌面会话、以及从网页和手机上发起的会话——它是个一站式控制台。网页和移动端的好处是可以随时随地发起任务：CLI 和桌面版都要求你在自己的笔记本前，但这很受限——有时你在外面（touching grass[15]）、散步，没开电脑。我都数不清见过多少人在外面举着开着的笔记本、用手机热点联网。这说明我们缺一个解决这个需求的产品。所以对我来说，移动端的意义就是让你在外面也能发起任务，不用到哪都背着开着的笔记本。

[15] touching grass：网络流行语，字面「摸摸草」，指离开屏幕出门接触真实世界。

Lenny：我太喜欢这个画面了。我见过有人在飞机上这样——现在都成梗了：「我得让这个 agent 跑完，不能关机，我需要 Wi-Fi。」

Cat Wu：至于 Cowork，它填的位置是：每个人做的很多工作，产出物不是代码。比如把 Slack 未读清零、收件箱清零；比如为即将到来的客户会议做幻灯片；比如写一份关于某个功能的目标或发布计划的快速文档。这些任务的产出都不是代码，而这正是 Cowork 最擅长的。所以我在脑子里的划分很简单：产出是代码，就用 Claude Code（终端、桌面或移动端）；产出是代码以外的任何东西，就用 Cowork。

Lenny：好。回到 PM 这个角色——我们前面聊到过一点，但这个话题值得展开：你觉得 PM 现在最需要培养的新兴技能是什么？或者说，AI 公司现在招 PM 时最看重什么？

Lenny：那这种技能怎么培养？是不是就是去用每一个模型，摸清每个模型的极限——就像你说的那种「品味」，对模型能做什么、擅长什么不擅长什么、哪里有变化，培养出直觉？

Cat Wu：我觉得就是花大量时间去用模型、跟模型对话。我特别喜欢做的一件事是让模型「自省」自己的行为。比如我注意到模型做了件出乎意料的事——它改了前端代码、跑了测试，但实际上根本没有打开界面看一眼——这时候直接问它「你为什么这么做」非常有用。有时它会说：「系统提示里有句话让我误解了」，或者「我没意识到前端验证也是任务的一部分」，或者「我把验证委托给了一个子 agent，子 agent 没跑测试，我也没检查它的工作」。很多时候，只要对「模型为什么做了那个决定」保持好奇，就能看清是什么误导了它，然后你就能去修 harness、把这个缺口补上。第二件有用的事是：找到那些你最信任、能对模型给出准确反馈的用户。总有一小撮人，在「说清楚某个模型或模型+框架组合好在哪里」这件事上明显强于其他人。给你反馈的人很多，但不是每个人的反馈都有同样的含金量。找到那么五六个你信任的人，对拿到快速反馈非常重要。第三件事有用、但不是人人都爱做：写 evals[23]。不需要写几百个才有用——写好 10 个就很关键，它能帮团队量化目标是什么、进展到哪了、还差什么。我觉得 eval 是个被低估的东西，更多 PM 和工程师都应该去做。

[51:35] Claude 的性格

[51:35] 新模型来了，就拆「拐杖」

Lenny：有个话题我想绕回来。你提到过，每次新模型出来，你们经常要回头重新审视已经做出来的东西。这很有意思，可能也挺让人崩溃的——「靠，我们刚发的东西，现在又得重做。」聊聊这个频率：每隔多久，新模型一来你们就得说「好，几个月前发布的这个功能得返工」？

Cat Wu：新模型到来时我们做的很多改动，其实是「删掉不再需要的功能」。很多时候，我们给产品加功能是给模型当「拐杖」——因为它自己还不会自然地做这件事。经典例子是 to-do list：Claude Code 刚发布时，用户让它做大规模重构，它会说「好，我需要改大约 20 个调用点」，然后改完 5 个就停了。我们就想：怎么逼着它记得把这 20 个全部改完？团队的 Sid 提出：「想想人类会怎么做——人会把要改的东西列个清单，就像在 VS Code 里查所有调用点，左侧一个列表，然后挨个替换。我们给 Claude 一个类似的工具怎么样？」于是他加了 to-do list，效果立竿见影——Claude 真的能把 20 个调用点全改完。但到了 Opus 4 和之后的模型，我们发现不用再逼它用了——它会自己自然地用。对早期模型，我们得不停提醒：「清单上的事都做完了吗？不做完不许收工。」对新模型，不用提示，它自然就会想着把清单清空。如今 to-do list 对用户来说仍然是个好功能——能更清楚地看到 Claude 在干什么——但说实话，它在产品里已经被大幅弱化了：模型用不用它都行，做出彻底的修改已经不再需要这根拐杖了。

Lenny：忘了谁在节目上说过的了：「模型会把你的 harness 当早餐吃掉。」我听到的正是这个意思：模型哪里不符合你的期望，你就得在上面加东西；而随着模型越来越聪明，这些外加的东西被一层层拆掉——让它做你想要的事，变得越来越简单。

Cat Wu：对。每次模型变强，我们都能删掉一大批提示词干预。而且我们每次发模型都真的做这件事：通读整个系统提示词，逐条反思——这一段提醒，模型还需要吗？不需要就删。不过新模型解锁的最令人兴奋的东西是全新的功能。有很多功能我们拿旧模型试过，但准确率不够高，没到能发布的程度。代码评审就是个例子：我们试过好几次做代码评审产品，以前也发过简化版——/code-review 这种斜杠命令[25]。直到最新的模型出来，我们才觉得：这个代码评审好到我们自己的工程团队都敢把「通过它」作为合并 PR 前的硬性关卡了。我们一直梦想 Claude 能成为一个可靠的代码评审者，能让我们有信心它抓得住大多数 bug。直到 Opus 4.5、4.6 和 Sonnet 4.6，我们才觉得：现在可以同时跑多个代码评审 agent，遍历整个代码库，综合出一份工程师在合并前必须处理的真实问题清单。这就是最新模型解锁的全新能力。

[25] 斜杠命令（slash command）：在 Claude Code 里以「/」开头触发的快捷指令，如 /code-review、/powerup。

Lenny：这又是节目里反复出现的一个规律：做一件「未来六个月内才可能做成」的东西，卡在能力边缘；等模型追上来，它就变成一个惊人的产品，而你已经领先所有人。

Cat Wu：对，完全正确。做一些「现在还不见得能跑通」的产品其实非常重要——这样你才知道差在哪。等新模型来了，直接把它换进你早就做好的原型里，看看新模型能不能把这个差距补上。

[65:12] 下一步：同时跑几百个 Claude

Lenny：Claude 和 Cowork 的走向——也就是愿景——你能讲多少？我猜你不想剧透太多路线图，但你们一直在加各种很赞的功能：从手机上派发控制、各种移动端能力。有没有什么方式能让大家理解这些东西长期指向的愿景？

Cat Wu：我们用「building block（积木）」来思考这件事。对 Claude Code 和 Cowork 来说，核心积木是「让单个任务成功」：你想产出某个结果，给它清晰的提示描述，它能不能持续产出合格的、你可以直接合并或分享给同事和外部受众的成果？任务就是那个核心积木。模型越聪明，任务成功率越高。然后我们看到大家开始并行做多任务——multi-clauding[26] 在 2025 年底开始流行，之后愈演愈烈。也就是说：单任务跑通了，现在你可以同时跑六个。模型再往后走，我们的外推是：下一步你可能同时跑 50 个、几百个 Claude。那需要什么样的基础设施？到那时候你不可能还在本机跑——内存根本不够。所以我们在想：怎么让你管理这么多 agent？它们大概率跑在远端；界面怎么设计，才能让你这个人知道哪些任务需要亲自看？怎么保证 agent 充分验证自己的工作——当一个任务说「完成了」，你能快速验证、并完全信任它确实按你的规格完成了？还有，怎么让这个过程自我改进——当你看到一个不合意的结果时，你给出反馈，模型在之后的每一次运行里都吸收它，永不再犯同一个错。这就是我们带着用户一起走的演进路线。

[26] multi-clauding：社区造词，指同时开多个 Claude 会话并行干活。

Cat Wu：把这句话告诉大家，其实是一种解放。在很多公司，角色被严格定义：这是 PM 干的、这是设计师干的、这是工程师干的；甚至团队的地盘也划得死死的——「这块代码库归我们碰，那块不许碰」。而「just do things」给大家的是一种被授权感：可以做决定，可以跨越团队边界，只为把事做成。

Lenny：这感觉是一种很重要的能力。有人叫它 agency（能动性）、「just do things」、行动优先——这些说法描述的都是同一件事：不等别人批准。

Cat Wu：对。这也是我特别推荐大家在人生某个阶段去创业公司工作的原因。对我改变很大的一段经历是在 Scale[34]——那会儿我们才 20 个人，没有任何流程，要解决的问题却非常大。我非常感谢 Alex（创始人 Alexandr Wang）和当时的团队：他们授权我和所有人放手去把事情想明白，没有「销售该干什么、运营该干什么、工程师该干什么」的边界——所有工具都摆在你面前，面前是一个宏大而棘手的命题，你可以用任何必要的手段去够到一个好答案。

Lenny：人几乎需要这样一段经历才能练出这种技能、才能对这种做法感到自如。因为太多人从学校一路走过来，受的训练都是「做我们让你做的事，就能拿好成绩」——你得把这套东西卸掉：「我就做那件需要被做的事，哪怕别人觉得蠢，只要我认为它是对的。」

[34] Scale：Scale AI，数据标注与 AI 基础设施公司，创始人 Alexandr Wang。Cat 早年在此任产品工程师（公开简历显示为 2018–2020）。

Lenny：我其实还有两个快速问题。最后两题。第一：Claude 思考的时候，会冒出各种……不知道你们管它们叫什么，动词？这些东西的术语是什么？

Cat Wu：「思考词」（thinking words）。

Lenny：思考词。有意思的是，这些词在那次源码泄露里全被扒出来了。你有最喜欢的思考词吗？

Cat Wu：我最喜欢「manifesting」（显化）[35]。我最喜欢的贴纸也是这个词。

[35] manifesting（显化）：流行文化词，指「强烈想象一件事来让它成真」。Claude 思考时界面会滚动显示各种「思考词」（如 pondering、manifesting），这些词在源码泄露中被公开，成为社区梗。

Lenny：当之无愧的冠军。好，最后一题——我也问过 Boris：如果 AGI 真在我们有生之年到来，工作不再是必须，你打算干什么？那么多时间用来干嘛？

Cat Wu：我觉得 AGI 扩散到整个社会还需要很长时间，所以眼下真正要做的是「把全世界一起带过来」。至于那之后——说个不正经的答案——我大概会去疯狂攀岩，搬到枫丹白露[36]，住在一万块石头中间，爬一阵子。还有太多想读的书：我的目标是一周一到两本，目前大概是 0.5 本，欠账不少。我们能从历史里学到的东西太多了，而我有太多领域不懂——物理、机器人、硬件、航空航天……有意思的题目太多了。所以我很期待去学——哪怕明知 AI 早就会了。

[36] 枫丹白露（Fontainebleau）：法国小镇，世界著名的抱石攀岩圣地，森林中散布着上万块岩石。

Lenny：Cat，这期太棒了，你真的很厉害。最后两个收尾问题：大家想关注你、联系你，去哪儿找？听众们有什么能帮到你的？

Cat Wu：联系我的最好方式是 Twitter，@_catwu。欢迎随时 @ 我，也欢迎私信——我会读所有私信，不是每条都回，但都会看。对我们帮助最大的，是告诉我们 Claude Code 和 Cowork 在哪里对你不好用。我们很感激大量的正面反馈，但真正让我们进步的养料是：边界情况、报错、那些可以被我们复现的具体失败任务。因为只要你能分享出来、我们能复现，我们就能在下一代模型和下一代 harness 里把它真正修掉。

Lenny：太好了。Twitter 上的大家提反馈可从来不客气——所以，继续砸过来吧。

Cat Wu：对，求分享——请一定把你们遇到的问题砸给我们。

Lenny：而且看到你们团队在 Twitter 上那么活跃、真的在回复大家，感觉特别好。所以这些反馈你们是真的在看、真的会响应的。

Cat Wu：对，我们非常感激大家这么投入地跟我们互动——这给团队带来巨大的能量。我们内部有个「user love」频道：大家分享的成功故事会贴到那里；产品问题则进反馈频道，这样整个大团队都能据此行动。

Lenny：知道这个真好，谢谢分享。Cat，非常感谢你来上节目。

Cat Wu：谢谢邀请。
